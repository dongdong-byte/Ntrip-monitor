> 관련 문서: [ini.md](ini.md), [sourcetable.md](sourcetable.md)

## 1. 전체 그림

```
기준국 (ANHN 안흥 등)          ← 정확한 좌표를 아는 곳에 설치된 GNSS 수신기
   │  RTCM 보정 데이터 생성
   ▼
캐스터 (www.gnssdata.or.kr:2101)   ← 여러 기준국 스트림을 모아 나눠주는 중계 서버
   │  NTRIP 프로토콜로 배포
   ▼
사용자 장비 (측량기, 드론, 농기계 …)  ← 보정 데이터를 적용해 cm급 측위 (RTK)
```

- GPS만으로는 위치 오차가 수 미터 난다(대기층, 위성 시계 오차 등).
- 기준국은 "내가 받은 GPS 값이 실제 위치보다 이만큼 틀렸다"는 **보정 정보**를 계속 내보낸다.
- 사용자 장비가 이것을 적용하면 cm 수준까지 정확해진다. 이 방식을 **RTK**라고 한다.

### 용어

| 용어 | 의미 |
|---|---|
| **RTCM** | GNSS 보정 데이터의 표준 메시지 형식. 원래는 표준을 만든 단체 이름(Radio Technical Commission for Maritime Services, 미국 해상 무선 기술 위원회) |
| **NTRIP** | RTCM을 인터넷으로 전달하는 규약 (Networked Transport of RTCM via Internet Protocol) |
| **캐스터** | 기준국 스트림을 모아 사용자에게 나눠주는 서버. 방송국에 해당 |
| **마운트포인트** | 캐스터 안의 개별 스트림. 방송국의 채널에 해당. 예: `ANHN-RTCM32` = 안흥 기준국의 RTCM 3.2 스트림 |
| **Sourcetable** | 캐스터가 제공하는 마운트포인트 목록. 공개 정보이며, `GET /` 요청으로 받는다 |
| **RTK** | 보정 데이터를 이용한 실시간 cm급 정밀 측위 |

## 2. NTRIP과 RTCM은 서로 다른 것

이름이 비슷해서 자주 헷갈린다. **v1, v2는 NTRIP 버전이고, 2.3, 3.2 같은 숫자는 RTCM 버전이다.**

| | 비유 | 버전 | 감시 프로그램에서 |
|---|---|---|---|
| **NTRIP** | 택배 **배송 방식** | 1.0, 2.0 | CLI `--protocol v1 / v2 / client` (기본값 `auto`) |
| **RTCM** | 상자 안 **물건의 형식** | 2.3, 3.0, 3.1, 3.2, 3.3, 3.4 | 마운트명 뒤의 `-RTCM23`, `-RTCM32` 등 |

두 축은 서로 독립적이다. NTRIP 1.0으로도 RTCM 3.2를 보낼 수 있고, NTRIP 2.0으로도 RTCM 2.3을 보낼 수 있다.

## 3. NTRIP 1.0과 2.0

| | NTRIP 1.0 (2004년) | NTRIP 2.0 (2009년) |
|---|---|---|
| 표준 문서 | RTCM 10410.0 | RTCM 10410.1 |
| 기반 | HTTP를 **흉내 낸** 방식 | **정식 HTTP/1.1** |
| 요청 | `GET /ANHN-RTCM32 HTTP/1.0` | `GET /ANHN-RTCM32 HTTP/1.1` + **`Ntrip-Version: Ntrip/2.0`** |
| 성공 응답 | **`ICY 200 OK`** | `HTTP/1.1 200 OK` |
| Sourcetable 응답 | `SOURCETABLE 200 OK` | `HTTP/1.1 200 OK` |
| 없는 마운트 요청 | 404 대신 **Sourcetable을 돌려줌** | 정식 **404** |
| 데이터 전송 | 그냥 흘려보냄 | chunked 전송도 가능 |

### 2.0이 나온 이유

- `ICY 200 OK`는 인터넷 라디오(SHOUTcast)에서 빌려온 응답이라 **정식 HTTP가 아니다.**
- 그래서 회사 방화벽이나 프록시가 이상한 응답으로 보고 차단하는 경우가 있었다.
- 이 문제를 해결하려고 정식 HTTP/1.1 기반으로 다시 정의한 것이 2.0이다.

### 두 버전이 공존하는 이유

현장에는 1.0만 지원하는 구형 측량기가 아직 많다. 그래서 캐스터들은 보통 두 버전을 모두 지원한다. 캐스터는 요청에 `Ntrip-Version: Ntrip/2.0` 헤더가 **있는지 없는지**로 어느 버전으로 답할지 결정한다.

### 실제 확인 결과 (2026-11-25, gnssdata Sourcetable 요청)

| 요청 | 응답 |
|---|---|
| v2 (HTTP/1.1 + `Ntrip-Version`) | `HTTP/1.1 200 OK` |
| v1 (HTTP/1.0) | `SOURCETABLE 200 OK` |

같은 캐스터가 요청 방식에 따라 다르게 답하는 것을 확인했다.

## 4. 감시 프로그램의 요청 방식 (`protocol`)

구현 위치: [ntrip/protocol.py](../ntrip/protocol.py)의 `PROFILES`

| 모드 | HTTP 버전 | `Ntrip-Version` 헤더 | User-Agent | 용도 |
|---|---|---|---|---|
| `v1` | 1.0 | 없음 | `NTRIP LivenessChecker/2.0` | 1.0 방식 검사 |
| `v2` | 1.1 | **있음** | `NTRIP LivenessChecker/2.0` | 2.0 정식 검사. **gnssdata 현재 설정** (ini 도입 후에는 `auto`가 기본값) |
| `client` | 1.1 | **없음** | `NTRIP Client 1.0` | 배포 클라이언트 요청 재현 (민원 재현) |
| `auto` | - | - | - | 시작 시 캐스터가 답하는 버전을 1회 탐지해 고정. **ini 도입 후 기본값.** 탐지의 한계는 [ini.md](ini.md) 3절 참고 |
| `both` | - | - | - | v1, v2로 각각 검사해 비교 (접속 2배, 진단용) |
| `all` | - | - | - | v1, v2, client로 각각 검사해 비교 (접속 3배, 진단용) |

### 민원 관련 배경

- gnssdata가 배포하는 `NtripClient_v2_1.exe`는 **HTTP/1.1로 요청하면서 `Ntrip-Version` 헤더를 보내지 않는다.** 바이너리 분석으로 확인했으며, User-Agent는 `NTRIP Client 1.0`이다.
- 그러면 캐스터가 이 요청을 **1.0으로 취급해 `ICY`로 답할 수 있다.** 2.0 응답을 기대하는 쪽과 결과가 갈릴 수 있다.
- 그래서 이 요청을 그대로 재현하는 `client` 모드를 만들었다. `all` 모드로 v1, v2, client의 판정이 갈리는 마운트를 찾을 수 있다. 판정이 갈린 마운트는 로그에 `변형별 판정 불일치`로 표시된다.
- 와이어샤크 확인: 캡처 필터 `tcp port 2101`, 표시 필터 `tcp.port == 2101`로 잡은 뒤 `Follow TCP Stream`을 열면 요청 헤더 원문(`Ntrip-Version` 송신 여부)을 직접 확인할 수 있다.

### 1.0 응답 처리에서 주의할 점 (코드에 반영됨)

- **ICY 응답 직후의 스트림**: 1.0 캐스터는 `ICY 200 OK\r\n` 뒤에 빈 줄 없이 곧바로 RTCM 바이너리를 보내는 경우가 많다. 헤더 끝(`\r\n\r\n`)을 기다리면 타임아웃이 난다. 그래서 첫 줄이 ICY면 거기까지만 헤더로 처리한다(`connection.py`의 `_split_icy`).
- **없는 마운트에 대한 응답**: 1.0은 404 대신 Sourcetable을 돌려준다. 그래서 응답에 `SOURCETABLE`이 있으면 `미등록`으로 판정한다(`policy.py`의 `decide_response`).
- **chunked 전송**: 2.0에서 chunked로 오면 청크 크기 줄을 데이터로 세지 않도록 디코딩한다(`chunked.py`).

## 5. RTCM 버전

| 형식 | 마운트 접미사 | 설명 |
|---|---|---|
| RTCM 2.3 | `-RTCM23` | 구형. 주로 GPS만 쓰는 DGPS용 |
| RTCM 3.0 | `-RTCM30` | RTK용 표준 |
| RTCM 3.1 | `-RTCM31` | 3.0에 메시지 추가 |
| RTCM 3.2 | `-RTCM32` | MSM 메시지 도입. GPS, GLONASS, Galileo, BeiDou 등 다중 위성 시스템 지원. gnssdata의 최신 형식 |
| RTCM 3.3 / 3.4 | (gnssdata에는 없음) | 메시지 추가. 3.4(RTCM 10403.4)는 2023년경 발표되었고, 최근 신규 장비가 지원하는 추세 |
| BINEX | `-BINEX` | RTCM이 아닌 별도의 바이너리 형식 |

- 장비마다 지원하는 형식이 달라서, 한 기준국이 여러 형식을 동시에 내보낸다. 그래서 관측소 하나에 마운트가 3~4개씩 있다.
- **RTCM 3.x는 버전이 올라가도 프레임 구조가 같다.** 메시지 종류만 추가된다.

### RTCM3 프레임 구조

```
[0xD3] [예약 6bit + 길이 10bit] [본문 0~1023바이트] [CRC24Q 3바이트]
```

- 첫 바이트는 항상 `0xD3`이다.
- 마지막 3바이트는 오류 검출용 CRC24Q 값이다.
- 본문의 앞 12bit가 메시지 번호다. 예: 1005(기준국 좌표), 1077(GPS MSM7 관측값).
- RTCM 2.3은 구조가 전혀 다르다(30bit 워드, 6-of-8 인코딩, 패리티). BINEX도 별도 형식이다. 따라서 프레임 검증은 형식별로 따로 구현해야 한다.

### 감시 프로그램에 미치는 영향

- 현재 로직(10초 안에 100바이트 이상 수신이면 양호)은 RTCM 버전과 관계없이 동작한다.
- 3차 작업(RTCM3 프레임 검증: `0xD3` 검출 + CRC24Q)은 3.0부터 3.4까지 똑같이 적용된다.
- **확인 필요**: 엑셀의 형식별 시트는 `BINEX`, `RTCM23`, `RTCM30`, `RTCM31`, `RTCM32`로 고정되어 있다. 새 캐스터에 `-RTCM34` 같은 마운트가 있으면 형식별 시트가 생기지 않는다(기관별 시트에만 기록된다).

## 6. 이 프로그램의 정체: 감시용 NTRIP 클라이언트

| | 일반 NTRIP 클라이언트 | 이 프로그램 |
|---|---|---|
| 예시 | `NtripClient_v2_1.exe`, RTKLIB, 측량기 내장 기능 | `liveness_main.py` |
| 접속 대상 | 마운트 **1개** | 마운트 **수백 개**를 병렬로 (현재 15개씩) |
| 접속 시간 | 몇 시간이고 **계속** | 1~10초만 받고 **바로 끊음** |
| 받은 데이터 | GNSS 수신기에 넘겨 위치 보정 | 바이트 수만 세고 버림 |
| 목적 | 정밀 측위 | 각 채널이 살아 있는지 확인 |

- 요청 방식(`GET /마운트명`, Basic 인증, ICY/HTTP 응답 처리)은 일반 클라이언트와 같다.
- **캐스터를 만드는 것이 아니다.** 캐스터는 기준국 수백 개의 데이터를 받아 수천 명에게 실시간으로 나눠주는 훨씬 큰 시스템이다.

### 고도화 방향

**방향 1: 감시 고도화 (권장)**

| 단계 | 내용 |
|---|---|
| 현재 | 바이트 수신 여부 |
| 3차 | RTCM 프레임 검증 (진짜 RTCM인지) |
| 다음 | 필수 메시지(1005, MSM 등) 수신 여부 |
| 다음 | 지연 시간, 끊김 빈도, 위성 수 같은 품질 지표 |

이 방향으로 가면 **NTRIP 품질 모니터링 시스템**이 된다. 코드 구조도 이 방향을 염두에 두고 짜여 있다(`probe.py`에 검증기를 주입하는 방식).

**방향 2: 사용자 클라이언트 (비권장)**

- 상시 접속과 자동 재접속, GNSS 수신기로 데이터 전달(시리얼, TCP), VRS용 GGA 위치 송신이 필요하다.
- 감시와 목적이 다르고, RTKLIB 같은 검증된 도구가 이미 있다.

### ④ 추가 학습: SNIP — RTCM 메시지 해설

- 자료: [An RTCM 3 message cheat sheet](https://www.use-snip.com/kb/knowledge-base/an-rtcm-message-cheat-sheet/)

- 볼 부분: Common Message Types, Multiple Signal Messages(MSM)
- 학습 목표: 한 RTCM 스트림 안에 기준국 정보, 관측값, 위성 궤도정보 등 서로 다른 메시지가 들어온다는 것을 이해한다.
- 메시지 번호를 전부 외울 필요는 없다. 오래된 설명도 포함되어 있으므로 최신 RTCM 3.4 전체 규격을 확인하는 자료로 사용하지 않는다.

### 권장 진행 순서

1. **토요일:** ① 이용방법과 ② 입문 강의로 GNSS·RTK·RTCM·NTRIP 용어와 서비스 이용 흐름을 익힌다.
2. **일요일:** ③ BKG 설명을 읽고 아래 세 파일의 흐름을 따라간다.
   - [protocol.py](../ntrip/protocol.py): v1·v2·client 요청의 HTTP 버전, Ntrip-Version 헤더, User-Agent 차이
   - [connection.py](../ntrip/connection.py): 응답 헤더와 본문을 분리하고 ICY·chunked 응답을 처리하는 방식
   - [probe.py](../ntrip/probe.py): 수신량을 측정하고 양호 기준을 판단하는 방식
3. **시간이 남으면:** ④ 메시지 해설로 RTCM 본문의 의미를 살펴본다.

### 공부 후 확인할 질문

- NTRIP v1·v2와 RTCM 2.3·3.4는 왜 서로 다른 버전인가?
- 같은 마운트인데 클라이언트의 요청·응답 처리 방식에 따라 결과가 달라질 수 있는 이유는 무엇인가?
- HTTP 200 응답만 받으면 정상이라고 판단해도 되는가?
- 현재 프로그램의 100바이트 수신 기준으로 확인할 수 있는 것과 확인할 수 없는 것은 무엇인가?

특히 다음 네 가지는 서로 다른 확인 단계다.

1. **200 OK를 받았다:** 서버가 요청에 성공 응답을 했다.
2. **데이터가 들어왔다:** 본문 바이트가 실제로 수신됐다. 현재 프로그램은 기준량 이상인지 확인한다.
3. **유효한 RTCM이다:** 프레임 구조와 CRC 등 형식·전송 무결성을 확인했다.
4. **정확한 위치 계산에 사용할 수 있다:** 데이터 시각, 필요한 메시지, 수신기 지원과 관측 조건 등을 추가로 확인해야 한다. CRC 통과만으로 측위 정확도가 보장되지는 않는다.

현재 요구사항인 **매시간 수신 상태 요약 메일**은 두 번째 단계에 해당한다. 프레임 검증과 측위 품질 평가는 별도 고도화 작업으로 구분한다.
